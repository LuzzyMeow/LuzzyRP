## 用户原话与约束

1. 「**设计请和现有主题保持一致**」——三方向一律落在既有「暖幕手记 × Claude」token 体系内，
   不得新增色相；差异只在信息架构 / 布局栅格 / 信息密度 / 层级表达 / 组件形态 / 动效叙事 / 排版尺度。

3. 字体策略选定 **全量 1:1 复刻 Web 端**（Lora + AlibabaSans + Alibaba PuHuiTi 3.0 三字重，约 +21MB）。

## 选定方向：A · 卷宗（Ledger）

**一句话定位**：对话是家，工具收进抽屉。会话优先 · 单列长读 · 抽屉式二级。

| 维度 | 规格 |
|------|------|
| 一级导航 | **无**——会话即家（首屏是会话列表） |
| 二级入口 | 右侧抽屉（记忆 / 技能 / MCP / 工作区 / 终端 / 设置），**2 跳** |
| 布局栅格 | 单列，内容边距 16dp |
| 信息密度 | 会话行 68dp、单屏 7 条会话 / 5 条记忆；正文 14px / 行高 1.65；caption 12px |
| 层级承担者 | 表面色阶（canvas → surface-soft → surface-card）+ 发丝线 |
| display 尺度 | Lora 17dp（较克制） |
| 标志动效 | 抽屉右滑 12dp + 淡入 200ms；返回 140ms |
| 主要风险 | 功能发现性弱（已用「头部条 + 全部助手」「底部输入岛键盘领接」缓解） |

### 关键组件映射（沿用 DESIGN.md token）

- **AI 气泡**：`surface-soft` + hairline，圆角 16dp；
- **用户气泡**：`#F1E3D9` + coral-300 边；
- **思考卡**：`surface-card` + hairline，执行中 live coral 描边，默认折叠；
- **工具卡**：单行 52dp（等宽工具名 + 状态 pill + 耗时），默认折叠；
- **步骤组**：新头部「N 步 · 总耗时」+ 缩进步骤行，组默认折叠；
- **输入岛**：`surface-card` 实底 + 22dp 圆角 + 44dp coral 发送键；
- **记忆行**：类型标签 + 正文 + `agent/user · 时间` + 相似度条（`primary-500`）。

## 与其它两方向的关系

- **B 工作台**（未选）：底部 4 tab + 双列栅格 + 状态仪表盘，密度最高、入口最浅，但气质偏控制台；
- **C 场记**（未选）：左轨 56dp + 右侧时间轴 + 编年体记忆，叙事感最强，但轨道占宽、小屏吃紧；
- 选定 A 后，B/C 的产出保留在 `assistant-v1/` 作为备选与后续迭代参考，**不删除**。

## 字体落地（硬性规定 4）

| 项 | 决策 |
|----|------|
| 转换 | `python tools/assistant-fonts.py --all`（woff2 → TTF，8 枚 / 21.2MB，落 `assets/assistant/fonts/`） |
| 正文/UI | **Alibaba PuHuiTi 3.0**（Regular/Medium/Bold）——覆盖中英文，与 Web 端观感一致 |
| display | **Lora**（拉丁）+ **PuHuiTi**（中文）经 `Typeface.CustomFallbackBuilder` 串成逐字形回退链（API 29+）；API 26-28 退化为 Lora + 系统衬线 |
| 偏差说明 | Compose 的 `FontFamily` **不做逐字形回退**（按字重/字形选字体），无法直接复刻 CSS 的 `Lora, PuHuiTi` 语义；故正文主族取 PuHuiTi、display 走自定义回退链。此为平台限制，已在 DESIGN.md 注明 |
| 体积 | 8 枚 TTF 约 21.2MB（用户已确认）；APK 约 43MB → 64MB |

## 改稿记录 · 侧栏折叠组动效收敛到设计令牌（2026-09-10，用户报告掉帧）

> **用户原话**：「解决侧边菜单栏多级抽屉菜单项打开时，动画不流畅的问题，帧数没达到手机刷新率」。

**门控判定（硬性规定 9 / huashu-design 豁免情形 2）**：属**已选定方向后的迭代**——不是新视觉
设计，而是既有折叠组（在线 / 高级 / 助手）的**时长收敛**，视觉语言（ease-out 族、无
`scale(0)`、高度揭示语义、chevron 同拍）**不变**，故不重走三方向硬门；按豁免条款在此落档。
同时满足**动效纪律**：改后时长正是 `DESIGN.md`「Motion」章规定的 **进入 200ms / 退出 140ms /
`cubic-bezier(0.23,1,0.32,1)`**（改前的 0.32s 是**上游**值，本就不在本项目令牌内）。

| 项 | 改前 | 改后 |
|----|------|------|
| 面板展开（进入） | `grid-template-rows 0.32s cubic-bezier(.22,1,.36,1)` | `200ms cubic-bezier(0.23,1,0.32,1)` |
| 面板收起（退出） | 同上（共用） | `140ms cubic-bezier(0.23,1,0.32,1)` |
| chevron 旋转 | `0.28s cubic-bezier(.22,1,.36,1)` | 与面板同拍（进 200ms / 退 140ms） |
| 视觉语义 | 高度揭示 + 同款缓动 | **不变** |

**依据（实测，非推断）**：真机 120Hz 量化——主线程不是瓶颈（每帧 layout 0.27ms + recalc
0.75ms + paint 0.6ms，rAF 稳定 8.3ms，`BeginFrame` P50 8.32ms）；瓶颈是 **GPU 栅格 ~5ms/帧 >
8.33ms 预算**。收敛窗口后动画帧数 38 → 24，单次展开掉帧 ~1.4 → ~0.8（同场交替 A/B：19/20 → 8/8）。
**掉帧率仍约 2~4%，本改动不消除**（GPU 地板）。完整数据与三条被排除的试探见
`docs/WORKLOG.md` 会话 48 与 `CHANGELOG.md` v1.5.0「优化」段。

## 改稿记录 · 开屏冷启动遮挡期渲染抑制（2026-09-10，用户报告开屏卡顿）

> **用户原话**：「开屏动画也总是会在最开始的时候卡顿一下，能不能再不牺牲视觉效果的情况下优化？跑满手机帧率」

**门控判定（硬性规定 9）**：**零视觉改动**的性能修复（不新增/修改任何视觉规格、动效时序、
色彩或排版；`DESIGN.md` Motion 章仅追加实测数据与实现注记）。按豁免条款「非设计的机械操作
（修 bug）不触发」+ 豁免情形 2 双重落档于此，不重走三方向硬门。

| 项 | 内容 |
|----|------|
| 症状 | 冷启动 UI 帧时中位 **17ms**（≈60fps）、GPU 90 分位 15ms、legacy 掉帧 **80.69%** |
| 病因 | ① 开屏入场动画**本身无问题**（LayerTree 实证全部 accelerated transform/opacity）；② 真正原因是**被开屏完全遮挡的应用主体仍在渲染**（3.2M px/帧）+ 启动期 GPU 瞬时负载 |
| 对策 | 遮挡期 `#app { visibility: hidden }`（保留布局）；入场 1.2s `.lsp-warm` 先解除、点击 `.lsp-dive` 原生兜底解除 |
| 结果 | UI 帧时中位 **7ms**、GPU 90 分位 6~7ms、legacy 掉帧 **4.1%** |
| 视觉 | **零差异**（遮挡期本就看不见应用主体；开屏为不透明纸面） |

**依据**：`docs/WORKLOG.md` 会话 48 追记（含四步诊断链与两条被否决方案）、`CHANGELOG.md`
v1.5.0「优化」段、`DESIGN.md` Motion 章开屏条目。
