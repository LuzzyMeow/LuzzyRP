## 0. 用户已接受的代价（写在这里，避免日后反复）

转 Compose **不是"换个容器"**，而是**重新设计**。用户已明确知情并选择继续，以下三条是这条路线的
**既定前提**，不再重复论证：

| # | 代价 | 说明 |
|---|---|---|
| 1 | **UI 不会 100% 还原** | 现在依赖的 Tailwind / CSS 布局模型 / `z-index` 层叠 / 浏览器原生文本选择 / `renderMarkdown` 的 HTML 输出，在 Compose 里**都没有对应物**。这不是"移植"，是"重新设计"。因此本计划第一步就是**先把设计语言定下来**。 |
| 2 | **上游同步能力退役** | RP-Hub（Vue 3）新功能不再能"同步 + 重放 patch"，此后每一次上游更新要么自行用 Kotlin 重写、要么永久落后。这是**持续成本**，不是一次性成本。 |
| 3 | **体量重写** | 前端应用逻辑约 **1.05 MB**（app.js 620KB + ui-components.js 230KB + data-services.js 90KB + runtime-services.js 31KB + built-in-content.js 63KB）+ 322KB 内嵌模板 + 整套 Tailwind 主题。 |

## 1. 第一步（本次）：**确定整体设计语言**，不写任何业务代码

**交付物**：`docs/DESIGN-compose.md`（Compose 版设计真源）+ 三方向差异化初稿。

**为什么第一步是设计而不是代码**：因为在这条路线上，"新 LuzzyRP 长什么样"是**前置未知量** ——
它同时决定组件库、主题 token、以及后面每个页面怎么写。先写代码 = 后面全部返工。

**强制设计门（硬性规定 9）**：本步属"UI 设计 / 前端设计"，**必须先完整阅读 4 项 SKILL 主文档**
（`huashu-design/SKILL.md` 64.6KB、`open-design/AGENTS.md` 45.7KB、`ui-ux-pro-max-skill/CLAUDE.md`
5.7KB、`awesome-design-md-main/README.md` 16KB），再产出 **3 个差异化方向**给用户选定。
**用户指定"复用 rikkahub"不豁免三方向门** —— 收窄的是风格，不转移选择权；三方向即
「复用 rikkahub 到什么程度、如何承担 RP 特有的界面」的三种取舍。

**rikkahub 复用前提（**已查证，结论是"直接复用源码"不成立**）**：

> **rikkahub 的许可证是 `AGPL-3.0`**（已读取其仓库 `LICENSE` 原文：
> `GNU AFFERO GENERAL PUBLIC LICENSE, Version 3, 19 November 2007`）。
> 这是**最强的一档 copyleft**，且比 GPL 更严（第 13 条对网络交互另有义务）。

对"直接复用前端"的含义（依据 AGPL-3.0 第 5 条 c 款：`You must license the entire work,
as a whole, under this License to anyone who comes into possession of a copy`）：

| 做法 | 后果 |
|---|---|
| **复制 rikkahub 的任何源码** | 整个 LuzzyRP（**整件作品**）必须转为 **AGPL-3.0** 分发 —— 包括上游 RP-Hub 的 Vue 前端 |
| 与现有许可的关系 | LuzzyRP 是 RP-Hub（CC BY-NC 4.0）的二创。把 AGPL-3.0 代码并入，会同时受两套条款约束，**存在实质冲突**，不是我能判断的范畴 |
| **借鉴设计语言、独立实现** | ✅ **不触发 copyleft** —— 版权保护的是"表达"而非"思想/功能/风格"。看它的界面、学它的观感、自己写代码，是通行做法 |
| 照抄具体 token 数值（色值/尺寸）与组件结构 | ⚠️ 这些**接近"表达"**，风险高于"借鉴风格"，应**重新设计**而非照搬 |

**因此本计划把"直接复用 rikkahub 的前端"修正为**：**以 rikkahub 为设计参照，产出 LuzzyRP 自己的
设计语言并独立实现**。这是唯一既达成用户目标（"整体设计语言"本来就属于设计层）、
又不动摇项目许可基础的做法。

**本步验收**：三方向初稿 + DESIGN-compose.md 草案 → 用户选一个方向 → 才进入 Phase 1。
**许可证的最终处置需用户拍板**（见 §6 第 1 条）。

## 3. 最高风险：**数据迁移**（必须在 P2 就做原型，不能拖到 P6）

现状：**全部用户数据在 WebView 的 IndexedDB 里**（`RPHubDB` / store `store`，键族
`rp_hub_chat_*` / `rp_hub_characters` / `rp_hub_presets` / `rp_hub_worldinfo` / `rp_hub_memories_*` /
`rp_hub_memories_settings` / `rp_hub_regex` / `rp_hub_branches_*` … 实测真机 24 键 / 14 键族）。

Compose 版本读不到它 —— **IndexedDB 属于 WebView 的 origin 存储，Kotlin 无法直接读**。
所以：

1. **WebView 不能提前删**。它必须活到"迁移完成"为止。
2. 迁移路径：一次性启动一个**隐藏 WebView** 读 `RPHubDB` → 序列化导出 →
   Kotlin 落进 Room → 校验条数/哈希一致 → 才允许切到 Compose 主界面。
3. **校验必须写死**：迁移前后对比「角色数 / 各会话条数 / 预设数 / 世界书数 / 记忆分片数」，
   不一致就**回退到 WebView 版本**而不是带着半份数据前进。
4. 这正对应 AGENTS 的核心纪律「同包名覆盖安装数据保留」——**数据丢了，老用户就没了**。

> 附带好处：v2.0 的 Kotlin 传输层（`chat/` 包，207 条单测）**在 v3.0 里原样可用** ——
> 它是纯 Kotlin、不依赖 WebView。P2 的流式上屏可以直接接它，这一步几乎是白捡的。
